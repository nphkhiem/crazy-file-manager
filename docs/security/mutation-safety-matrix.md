# Mutation safety matrix

Rename and Move to Trash are the only two filesystem-mutating operations this application performs. This matrix maps each safety guarantee this app makes about those operations to the specific tests that prove it, across both supported test environments (unit tests against a real local filesystem, and UI tests against the real running app). Every row below was verified against the real test file, not assumed from a design doc.

| Guarantee | Unit test evidence | UI test evidence |
|---|---|---|
| Never permanently deletes | `FoundationTrashExecutor.trash(at:)` calls `FileManager.default.trashItem(at:resultingItemURL:)` exclusively — the native macOS "move to Trash" API, never `removeItem` — confirmed by reading `FoundationTrashExecutor.swift` directly. `FoundationTrashExecutorTests.givenAnExistingFile_whenTrashed_thenTheSourceNoLongerExistsAtItsOriginalPath` and `.givenANonexistentSource_whenTrashed_thenItThrows` prove the wrapper's real filesystem behavior. | `FocusRestorationUITests`/`KeyboardOperabilityUITests`/`LargeResultSetKeyboardUITests` all drive real Move to Trash confirmations against real fixture files. |
| Never mutates a target whose live identity no longer matches what the user selected (TOCTOU / stale-target substitution) | `MutationPreflight.validate` is proven directly: `MutationPreflightTests.givenUnchangedFile_whenValidated_thenPreflightAccepts`, `.givenFileDeletedSinceExpectedEvidenceWasCaptured_whenValidated_thenPreflightRejectsAsMissing`, `.givenFileReplacedWithADifferentFileAtTheSamePath_whenValidated_thenPreflightRejects`, `.givenFileMovedToADifferentParent_whenValidated_thenPreflightRejects`, `.givenAGuardedMutationCallSite_whenPreflightRejects_thenTheMutationClosureIsNeverInvoked` (proves the mutation closure itself is never called on rejection, not just that an error is returned). | Not independently re-proven at the UI layer — this is exclusively a filesystem-race concern, exercised more precisely and more reliably at the unit level against a real filesystem than a UI test could reproduce. |
| `RenameOperation`/`TrashOperation` re-validate immediately before mutating and refuse a target that changed since the user's own preflight snapshot was captured | `RenameOperationTests`: `.givenATargetDeletedSincePreflightEvidenceWasCaptured_whenRenamePerforms_thenItRejectsWithoutInvokingTheExecutor`, `.givenATargetThatBecameHardLinkedSincePreflightEvidenceWasCaptured_...`, `.givenATargetReplacedWithADifferentFileAtTheSamePath_...`, `.givenATargetReplacedWithASymbolicLinkAtTheSamePath_...`, `.givenTargetPermissionRevokedSincePreflightEvidenceWasCaptured_...`. `TrashOperationTests`: the equivalent deleted/hard-linked/permission-revoked cases, plus `.givenAnEligibleTargetWhoseExecutorFails_whenTrashPerforms_thenItRejectsWithoutClaimingSuccess` (an executor-level failure is never misreported as success). | — |
| A hard-linked (ambiguous-identity) item is never eligible for Rename or Move to Trash in the first place | `RestrictionPolicyTests.givenSharedHardLinkedItem_whenClassified_thenStateIsHighRisk`, `.givenEachRestrictionReason_whenCapabilityComputed_...` (confirms the `.highRisk` reason maps to both `canRename: false` and `canTrash: false`). | — |
| OS-protected, application-managed, package-internal, and read-only-volume paths are never eligible for Rename or Move to Trash | `RestrictionPolicyTests.givenSystemFrameworksPath_...`, `.givenApplicationSupportPath_...`, `.givenPackageDescendantItem_...`, `.givenReadOnlyVolumeItem_...`, and the boundary/root cases (`.givenTreeRootItem_...`, `.givenVolumesMountRootItself_...`). | — |
| Basic input validation runs before any live filesystem check, and produces an honest, specific reason | `RenameValidationTests`: empty name, path-separator characters, `.`/`..`, invalid platform characters (null byte), name collision with a sibling, each mapped to a distinct `RenameValidationError` case; Unicode names and the item's own unchanged name are proven to validate cleanly with no false rejection. | `FocusRestorationUITests.test_givenAnInvalidRenameIsSubmitted_whenValidationFails_thenTheReasonIsAnnouncedAndTheFieldStaysFocused` (submits an empty name through the real inline rename field and confirms the exact validation message appears with focus retained). |
| Rename and Move to Trash are unavailable app-wide in the public release build until independent review is accepted | `RestrictionPolicyTests.givenTheReleaseGateIsActive_whenCapabilityComputedForAnOtherwiseNormalItem_thenBothActionsAreDisabledWithAnHonestReason`, `.givenTheReleaseGateIsActive_whenCapabilityComputedForAnAlreadyRestrictedItem_thenTheOriginalRestrictionReasonWins`. | `PublicReleaseGateUITests` (both the gate-active and gate-inactive cases, against the real running app with a real backing file). |
| A downloaded update artifact is never revealed to the user if it does not match the signed metadata's checksum | `UpdateCheckSessionTests.givenTheDownloadedArtifactHashDoesNotMatchTheSignedMetadata_...`, `.givenAGenuinelyTamperedDownloadedArtifact_whenConfirmedWithTheRealVerifier_...` (real tampered bytes, real hashing, real Ed25519-signed metadata). | Not exercised at the UI layer — confirmed untestable via XCUITest's inability to reliably click `.confirmationDialog`/sheet buttons on this platform (see `SettingsUITests`' download-flow test, which only reaches the confirmation sheet and cancels, a known, documented platform limitation from Ticket 15). |

## Known coverage gap

The live confirmation-dialog Move-to-Trash button click path (the actual "Move to Trash" button inside the native `.confirmationDialog` sheet, as opposed to keyboard-only Command-Delete triggering the dialog itself) cannot be reliably driven by synthesized XCUITest clicks on this macOS/Xcode version — confirmed generic during Ticket 15 (both the destructive button and Cancel fail identically). This is a test-infrastructure limitation, not a gap in the production mutation-safety code itself, which is independently and thoroughly proven at the unit level above. A human tester (or a future XCUITest/Xcode version) should still exercise this exact click path manually before the Rename/Trash public-release gate (see above) is ever turned back off.
